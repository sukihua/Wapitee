# Project Handover Brief

Build a handover doc for someone taking over a project. They need the full picture fast: what the product is, where the project stands, who does what, what was decided, and what is still open.

## 1. Read everything, in date order

- Read every file in full: PDFs, chat exports, reports, surveys. Render pages as images when a file has charts or ad creatives.
- Sort sources by date. When a newer source contradicts an older one, use the newer one, and record the conflict in a table (see section 4).
- Treat AI-generated meeting notes as lower confidence than data reports. When they disagree, go with the report and say so.
- Check whether each file actually belongs to this project. If a file is from another client, leave it out of the brief and say so in one line.
- Chat logs hold what formal notes leave out: decisions, disagreements, failures, and who really does what. Mine them carefully.

## 2. Doc structure (a Docs artifact, unless the user asks for another format)

0. **Opening:** a one-sentence product definition in bold, then the current stage and next milestones, then the 2–3 decisions that must be made this week, then the sources used.
1. **Project overview:**
   - scope of work, as a table: module | our side | client side
   - current status
   - budget: what is known; which items have no amount yet; CPL is not CAC
   - shoots and creative assets, with dates and specs
   - team, as a table: person | side | responsibility
   - key accounts and document links
2. **Timeline:** a drawn diagram of milestones, past and planned, with a dashed "today" line.
3. **Product:**
   - positioning
   - form and how it works, as a table
   - software boundary: what the product does NOT do
   - specs, as a table: item | current claim | status
   - core selling points, ranked by user data
   - naming, as a table: candidate | data | who backs it
   - pricing and SKU
   - look and colors
4. **Audiences and pretest data:**
   - start with a one-line conclusion and a summary table of each audience segment
   - give each segment its own heading: who they are / how they performed / what to do next
   - then: how segments were defined, caveats before reading the data, CPL by phase, creatives, copy and ad placements (with screenshots of the top creatives), demographics, long-tail audiences, research findings, on-site funnel, open-ended answers grouped by theme
5. **Off-the-record discussions:**
   - strategic disagreements, as a table: topic | client view | our view | status
   - how the client works
   - things that went wrong
   - other context the new PM must know
6. **To-dos, risks, open questions:**
   - this week (checklist), before launch (checklist)
   - risks
   - conflicting sources, as a table: item | version A | version B | recommendation
   - questions nobody has answered yet
   - sources

## 3. Writing standard

- Define the product at the category level, in professional words. Example: "a wearable voice-input device that lets users speak at normal volume in shared spaces while reducing sound leakage." Avoid literal descriptions ("worn on the mouth") and coined jargon.
- Do not present unvalidated things as settled. Example: who the target users are, while the pretest is still validating them.
- Put the key finding where the eye lands first: a bold conclusion line, a table, or a heading. Never bury it mid-sentence.
- Keep the tone formal and precise. Every claim carries a number, a date, or a source.
- For product questions the materials don't answer (for example, "does it transcribe like Wispr Flow?"), say plainly that it is unconfirmed. Give the most reasonable reading, and list the questions to ask.
- Never drop pretest data when restructuring. Before a rewrite, list every data block (phases, creatives, copy, placements, funnel, open-ended answers) and confirm each one is still in the new version.

## 4. Before delivering

- Compare against any other summary the user provides, and fill in missing facts. Mark information you could not verify as "cited from X".
- Look at the timeline diagram and the screenshots as rendered.
- Reply to the user with a short message: what changed and what is still unconfirmed. Do not recap the doc.
